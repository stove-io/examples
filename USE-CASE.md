# Commerce use-case

Every commerce example implements this contract. The Stove test in `usecase/e2e` is the same for each suite. Each `StoveConfig` extends the shared `EcommStoveConfig` and only supplies its runner and the way configuration is passed.

Every application implements the same product, checkout, statistics, background-work, gRPC-query, and streaming scenarios. JVM suites also demonstrate direct application bean access.

## HTTP

| Request | Response |
| --- | --- |
| `GET /health` | `200` `{"status":"UP"}` |
| `POST /api/products` with `{"name": string, "price": number}` | `201` `{"id": string, "name": string, "price": number}` |
| `GET /api/products/{id}` | `200` with that shape, or `404` when the id is unknown |
| `GET /api/products` | `200` JSON array of products |
| `POST /api/orders` | Checks fraud, inventory and payment, then persists a confirmed order and publishes events; unavailable inventory returns `409`, declined payment returns `502` |
| `GET /api/orders/{id}` | `200` with the persisted order, or `404` |
| `GET /api/orders/stream?userId=...` | `200` NDJSON stream of the customer’s persisted orders |

`id` is a UUID generated by the app. A body that is not this JSON object returns `400`. Process and container readiness calls `GET /health`. The shared test does not.

## PostgreSQL

Stove creates the tables. Applications only read and write them. The shared streaming test creates products through HTTP, inserts orders as PostgreSQL fixtures, and checks the bounded stream through Stove’s HTTP DSL.

```sql
CREATE TABLE IF NOT EXISTS products (
    id VARCHAR(255) PRIMARY KEY,
    name VARCHAR(255) NOT NULL,
    price DECIMAL(10, 2) NOT NULL
);
```

## Kafka

| Topic | Direction | Body |
| --- | --- | --- |
| `product.created` | published after a successful insert | `{"id","name","price"}` |
| `product.update` | consumed, then the matching row is updated | `{"id","name","price"}` |
| `product.updated` | published after an existing row is updated | `{"id","name","price"}` |
| `showcase.orders.created` | published after checkout, consumed to update customer statistics | `{"orderId","userId","productId","amount"}` |
| `showcase.payments.processed` | published after payment succeeds | `{"orderId","transactionId","amount","success"}` |
| `order.confirmation.sent` | published after a confirmation job succeeds | `{"orderId","userId","productId","amount"}` |
| `customer.statistics.updated` | published after the statistics transaction completes | `{"orderId","userId"}` |

The HTTP response is still `201` when publishing `product.created` fails. An update for an unknown id changes zero rows and produces no `product.updated` event. Malformed records can be discarded and committed; database failures are not successful updates. The test waits for consumption and the subsequent publication before querying PostgreSQL, so receipt is not mistaken for completion.

## Background work

Go, TypeScript, and Rust enqueue `order_confirmation` jobs in River. JVM applications schedule the same confirmation with db-scheduler. The shared checkout test uses the registered `river` Stove system to match the order's arguments and wait for successful job completion. The system observes committed PostgreSQL state using notifications, so a published confirmation event alone is not treated as proof that River completed the job. JVM suites use a scheduler listener for the same completion assertion.

## Tracing

Export OTLP to the receiver Stove opens, and propagate W3C `traceparent`. These server span names are required because the test matches them as substrings:

- `POST /api/products`
- `GET /api/products/{id}`
- `GET /api/products`

The get-by-id span includes the literal text `{id}`.

## Configuration

Process and container applications read:

| Variable | Meaning |
| --- | --- |
| `APP_PORT` | HTTP port, bound on all interfaces |
| `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER`, `DB_PASS` | PostgreSQL |
| `KAFKA_BROKERS` | bootstrap servers |
| `INVENTORY_URL`, `PAYMENT_URL`, `FRAUD_GRPC_TARGET` | checkout dependencies supplied by the suite |
| `OTEL_EXPORTER_OTLP_ENDPOINT` | `host:port` of the span receiver |

The Ktor and Spring Boot applications receive the same values as runner parameters. Go uses franz-go. Go, TypeScript, and Rust receive `STOVE_KAFKA_BRIDGE_PORT`; their local bridges can optionally use `STOVE_KAFKA_BRIDGE_HOST` (default `localhost`). With no port, the bridge is disabled. The observer protocol represents headers as strings and cannot distinguish a null value from empty bytes.
